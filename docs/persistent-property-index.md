# 拾物索引持久化与增量更新

MySQL 的 `lost_property` 是事实来源。`LostPropertyIndexService` 保存物品名称、特征、记录 ID 和向量，联系人姓名、手机号及账号 ID 不写入索引。

## 运行方式

- 首次启动：从数据库导入全部拾物记录，计算向量并生成索引文件。
- 再次启动：恢复文件中的向量，核对数据库；仅新增或物品描述变化的记录重新计算向量，已删除记录从索引移除。
- 拾物登记新增或修改成功：根据数据库生成或已确认的记录 ID 立即同步。若存在 Spring 事务，在提交后同步；回滚不更新索引。
- 索引失败不撤销已经保存的登记，页面会提示索引同步中。默认每 60 秒核对数据库补偿；进程意外终止留下的同步缺口也在下一次启动补齐。
- 外部直接修改或删除数据库：下一次核对同步。搜索返回候选前会再次读取数据库，过滤已经删除或描述变化的旧线索。
- 查询只计算查询文本的向量，复用物品向量；不会每次重新嵌入全部登记。返回 `List<String>`，每个元素是候选物品的 JSON。

物品匹配覆盖所有用户的拾物记录，不按失主手机号或用户 ID 过滤。查询本人丢失登记、修改本人登记仍保留所有者校验。向量相似度只是候选依据，不代表物品已确认归属或已归还。

## 配置

`src/main/resources/application.properties`：

```properties
lost-found.index.path=${LOST_PROPERTY_INDEX_PATH:./data/lost-property-index.json}
lost-found.index.model-version=bge-small-zh-v15-q-v1
lost-found.index.reconcile-delay-ms=60000
```

默认文件相对于应用工作目录。例如从工程根目录启动，保存到工程根目录的 `data/lost-property-index.json`。`data/` 已加入 `.gitignore`。换启动目录时应设置 `LOST_PROPERTY_INDEX_PATH` 为固定绝对路径；容器部署需将该目录挂载到持久卷。

更换向量模型或调整物品向量文本格式后，修改 `model-version`。应用将在下一次启动时重新计算全部物品向量，避免混用不同模型生成的向量。

无需数据库表结构变更，也无需额外安装向量数据库。原聊天查询工具和 `/ai/embedding-query` 已改用同一个索引；原管理员 `/ai/embedding-index` 接口改为数据库核对与修复，不再写桌面的中间文件或重复追加向量。

## 文件与一致性

每次变化构建新快照，写入同目录临时文件并强制刷盘，再原子替换正式文件，成功后发布内存快照。磁盘写入失败保留之前的内存和正式文件，下一次核对重试。索引格式损坏会让启动失败，保留原文件供检查；停机备份损坏文件并将其移出配置路径后，下一次启动可从数据库重建。

向量计算为增量，当前实现的每次持久化仍写完整快照、内存查询索引也随快照重建；定时核对读取全表的三个物品字段。适合当前单实例、小到中等数据量项目。跨 MySQL 与文件采用最终一致性，故障恢复依赖数据库核对，不承诺两者原子提交。

索引目录通过文件锁限制一个应用实例使用，不支持多实例共享写入。未来多实例或大数据量部署应迁移到支持按记录 ID upsert/delete 的持久化向量服务，并使用事务 outbox 传递变更。

## 验证

```powershell
./scripts/verify-persistent-index.ps1
```

脚本临时生成单独的测试 POM，仅编译本次索引测试，执行后删除；不会修改正式 `pom.xml`。这是因为项目旧测试仍使用之前的 Assistant 两参数签名，目前无法全量编译。

17 个测试使用模拟数据库、模型和临时目录，覆盖：磁盘恢复、增量替换、停机变化补偿、跨用户匹配、联系人不进入索引、模型失败、文件写入失败、事务提交/回滚、删除清理、模型版本迁移、损坏文件和并发文件锁，以及业务保存后的同步调用。

真实联调步骤：

1. 启动应用，确认日志出现“拾物索引核对完成”。
2. 账号 A 登记丢失物品；账号 B 登记拾到特征相同的物品并确认保存。
3. A 查询已登记物品，检查能否取得 B 的候选拾物线索。
4. B 修改物品特征并确认，检查索引文件中该 ID 只有一条且描述已更新。
5. 重启应用，A 再查询，无需手动构建索引。

模拟测试不验证真实模型的召回率、真实 MySQL 字段映射或已部署目录权限；需按上述步骤验证实际环境。
